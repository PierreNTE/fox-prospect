## 0. Synthèse exécutive

### Ce qui a changé depuis juin (et qui est bien)

L'équipe a exécuté vite : `ai_runs` (comptabilité au token près), kill-switch budget mensuel, recherche 2 passes (Haiku extraction + Sonnet jugement), cache de fraîcheur TTL, file de jobs asynchrone avec verrou optimiste et auto-réparation des zombies, collecteurs gratuits (BOAMP, France Travail, SIRENE), scoring déterministe (`lib/scoring.js`), timeline `events`, statuts commerciaux propres, validateurs de sorties LLM, SSR, ⌘K, mode sombre, harnais d'eval. **C'est un très bon MVP solo.**

### Les 7 verrous qui restent (par ordre de gravité)

| # | Verrou | Preuve dans le code | Conséquence |
|---|---|---|---|
| 1 | **Le scoring déterministe n'est pas branché.** La table `scores` n'a **aucun writer** ; `computeScores` n'est appelé que côté client (ProspectClient.js:600) avec `firmographics: {}` (business score figé à 50). Les priorités et le tri restent sur `fit_score` LLM opaque. | `grep from("scores")` → 0 résultat hors migration | Le cœur de la promesse ("priorisation fiable") repose encore sur un chiffre non reproductible |
| 2 | **Double modèle d'entreprise** : `accounts` (uuid, clé = nom) ET `companies` (bigint, clé = SIREN) coexistent. Les collecteurs rattachent par `ilike '%premier-mot%'` (collect-boamp.js:83) — "Société Générale" matche "Société Générale de Nettoyage". | 2 tables, 3 stockages de signaux | Doublons, signaux mal rattachés, scoring faux |
| 3 | **Trois sources de vérité pour les signaux** : `research.signals` (JSONB), `accounts.signals` (JSONB), `company_signals` (table relationnelle). Le heat score lit le JSONB, les collecteurs écrivent la table, la NBA lit le JSONB de research. | `computeAccountHeat` vs `ingestBoampSignals` | Les signaux gratuits collectés n'alimentent **ni** le scoring **ni** les priorités |
| 4 | **Chaque qualification re-paye la recherche entreprise.** 5 prospects chez Decathlon = 5 × extraction web complète de l'actu Decathlon. Aucune mutualisation par compte. | `runResearch` cache par `prospect_id` uniquement | Coût ×N par compte multi-contacts — le levier coût n°1 |
| 5 | **Les hooks/brouillons sont générés pour des prospects jamais contactés.** La passe de jugement produit hooks + score pour 100 % des prospects qualifiés, alors que ~la moitié ne seront jamais approchés. | `judgmentSystemPrompt` sort les hooks | ~40 % des tokens de sortie Sonnet dépensés pour rien |
| 6 | **Migrations en roulette russe** : `events` est défini **deux fois** (partitionné dans `migration-v1.sql`, non partitionné dans `migration-v3.sql`), les deux en `create table if not exists`. Le schéma réel dépend de l'ordre d'exécution manuel dans le SQL Editor. | migration-v1 §4 vs migration-v3 §1 | Base non reproductible, onboarding SaaS impossible |
| 7 | **Mono-tenant structurel** : pas de `users`/`orgs`, RLS sans policies (service_role partout), session = hash statique de `user:password` sans expiration serveur ni révocation. | `lib/auth.js`, `middleware.js` | Zéro client au-delà de Pierre sans refonte auth |

### Le chiffre qui compte

Coût actuel d'une qualification : **~0,045 €** (2 passes, 2 web_search). Après les optimisations du §2 (mutualisation compte, jugement conditionnel, hooks différés, sorties structurées, Batch API, enrichissement déterministe) : **~0,008-0,012 €**, soit **÷4 à ÷6, sans perte de qualité mesurable** (le harnais d'eval existe pour le prouver). À 330 prospects/mois le budget passe de ~15 € à ~3 € ; à l'échelle SaaS (10 000 prospects/mois), de ~450 € à ~90 €.

## 1. Architecture

### 1.1 État des lieux

```
Next.js 14 App Router (JS, pas de TS)
├── app/api/*          27 routes — logique métier majoritairement extraite dans lib/ ✅
├── lib/*              couche service correcte (research, scoring, budget, nba, data…)
├── Supabase           Postgres + RLS "fermée" (service_role only), 11 fichiers SQL manuels
├── Crons              2 crons Vercel (Hobby max) + 2 workers GitHub Actions
└── Scraping           Python local + GitHub Actions (Brave API) → scrape_jobs/scrape_results
```

**Forces réelles** : la logique coûteuse est bien factorisée (`runResearch`, `analyzeAccount`, `drainJobQueue` réutilisés par routes ET crons) ; les garde-fous budget sont systématiques ; le contournement de la limite Vercel Hobby (drain de la file greffé sur le cron de veille + worker GitHub Actions) est astucieux et documenté.

**Faiblesses structurelles** :

1. **Deux systèmes de files** (`jobs` drainée par cron Vercel/worker GH, `scrape_jobs` drainée par le worker Python) avec des conventions différentes (`payload` vs `params`, `error` vs statuts distincts). Acceptable aujourd'hui, mais tout nouveau type de tâche pose la question "quelle file ?".
2. **Orchestration éclatée sur 3 plateformes** (Vercel cron, GitHub Actions, navigateur). Le chemin SaaS impose de consolider : soit tout sur GitHub Actions/Inngest/QStash qui pingue des endpoints, soit Supabase `pg_cron` + Edge Functions. Recommandation : **garder la table `jobs` comme unique file, déclencher le drain toutes les 15 min via le worker GitHub Actions existant** (`process-jobs-worker.yml` fait déjà ça — il suffit d'en faire le chemin nominal et de rétrograder le cron Vercel en filet de sécurité).
3. **N+1 restants** : `ingestBoampSignals` fait 2-3 requêtes **par signal** (ilike + count dédup + insert) soit ~150 requêtes/run ; `POST /api/prospects` rattache les comptes un par un ; `auto-qualif` vérifie l'opt-out contact par contact. À corriger par des requêtes ensemblistes (`in (...)`, `insert ... on conflict`).
4. **Pas de tests** (hors eval LLM), pas de lint, pas de TypeScript. `computeScores`, `parseSignalDate`, `computeNba`, `extractJson` sont des fonctions pures **idéales pour des tests unitaires** — 2 h de travail, filet de sécurité permanent.

### 1.2 Architecture cible (SaaS)

```
┌────────────── INGESTION (gratuite, sans LLM) ──────────────┐
│ SIRENE / BOAMP / France Travail / BODACC / scraping Brave  │
│        → companies (SIREN = clé unique d'entreprise)       │
│        → company_signals (source de vérité UNIQUE)         │
└──────────────────────────┬─────────────────────────────────┘
                           ▼
┌────────────── SCORING (déterministe, gratuit) ─────────────┐
│ recompute_scores (job) → table scores (écrite, enfin)      │
│ file priorisée = urgency × business × accessibility        │
└──────────────────────────┬─────────────────────────────────┘
                           ▼
┌────────────── LLM (réservé au haut de la file) ────────────┐
│ 1. company_research (mutualisée par SIREN, TTL 14 j)       │
│ 2. contact_research (delta contact, Haiku, léger)          │
│ 3. génération hooks/brouillons À LA DEMANDE uniquement     │
│ Batch API pour tout l'autonome (-50 %)                     │
└──────────────────────────┬─────────────────────────────────┘
                           ▼
┌────────────── APP (multi-tenant) ──────────────────────────┐
│ Supabase Auth + orgs + RLS par org_id                      │
│ / (daily queue) · /pipeline (kanban) · /accounts · /...    │
└────────────────────────────────────────────────────────────┘
```

Décisions structurantes :
- **`companies` absorbe `accounts`** (le SIREN devient LA clé ; `accounts` devient une vue de compat le temps de la migration). Un seul rattachement, plus d'`ilike`.
- **`company_signals` devient l'unique stockage de signaux** ; `research.signals` et `accounts.signals` (JSONB) sont backfillés dedans puis gelés.
- **La table `scores` est écrite** par un job de recalcul (au signal nouveau, au changement de firmo, cron quotidien) et lue par la liste, les priorités et le tri.
- Stack conservée : Next.js + Supabase + Vercel est le bon choix (pas de refonte gratuite). Migration TypeScript progressive (nouveaux fichiers en `.ts`, `checkJs` d'abord).

## 2. Optimisation IA — le tableau demandé

Tarifs (constants.js) : Sonnet 2,8 €/M in · 14 €/M out ; Haiku 0,25 €/M in · 1,25 €/M out ; web_search 9,3 €/1000.

| Appel | Modèle actuel | Coût actuel | Optimisation | Coût optimisé | Gain | Impact qualité |
|---|---|---|---|---|---|---|
| **Research passe 1** (extraction) | Haiku + 2 web_search | ~0,022 € | **Mutualiser par entreprise** (cache `company_research` par SIREN, TTL 14 j) : seuls ~30 % des runs paient encore la recherche ; passe contact réduite à 1 search | ~0,009 € (moyenne) | **-60 %** | Nul (mêmes faits, plus frais car partagés) |
| **Research passe 2** (jugement) | Sonnet, sort signaux+score+hooks | ~0,028 € | (a) **Skip si `facts=[]`** (~30 % des cas) → résultat déterministe "aucun signal" ; (b) **retirer les hooks** (différés à la génération) → sortie 1500→500 tokens ; (c) basculer sur **Haiku** après validation eval | ~0,004 € | **-85 %** | À mesurer via `npm run eval` ; (a) et (b) sont sans risque, (c) à valider |
| **Generate** (brouillons) | Sonnet sans search | ~0,015 € | Garder Sonnet (qualité rédactionnelle = cœur de valeur). Ajouter les hooks ici (déplacés du jugement). Ne générer **que sur action utilisateur** (déjà le cas ✅) | ~0,018 € | -0 % (transfert) | Positif : hooks générés avec le signal déclencheur frais |
| **Analyze account** | Sonnet + 2 search, 4000 tokens out | ~0,07 € | Même schéma 2 passes que research (Haiku extrait, Sonnet ne juge que si signaux) ; fusionner avec `company_research` (c'est la même recherche !) | ~0,02 € | **-70 %** | Nul — c'est littéralement une duplication actuelle |
| **Enrich email** | Sonnet + web_search | ~0,05 € | **Remplacer par du code déterministe** : pattern `prenom.nom@domaine` + vérif MX + patterns connus par domaine (la logique existe déjà dans `waterfall.py` !). LLM en fallback uniquement si domaine inconnu | ~0,002 € (LLM sur ~10 % des cas) | **-95 %** | Positif : le LLM "devine" aujourd'hui ce que le code calcule mieux |
| **Brief** (P4) | Sonnet + search, à la demande, caché | ~0,07 € | Déjà bien conçu (manuel + cache + budget). Réutiliser `company_research` comme contexte pour réduire les searches à 1 | ~0,05 € | -30 % | Nul |
| **Import LinkedIn** | Sonnet + search | ~0,04 € | Passer l'identification sur **Haiku** (tâche d'extraction pure) | ~0,01 € | -75 % | Faible (à vérifier eval) |
| **Réparation JSON** (callClaudeJson 2e passe) | même modèle, re-prompt complet | ~5 % des appels ×2 | **Sorties structurées** : forcer le JSON via tool_use avec `input_schema` (le modèle ne PEUT pas répondre autre chose). Supprime la passe de réparation ET `extractJson` | 0 € | **-100 %** de la réparation | Positif : plus aucune troncature/preambule possible |
| **Tous les jobs autonomes** (file `jobs`) | API temps réel | — | **Message Batches API** : la file est déjà asynchrone, le batch est fait pour ça. -50 % sur tous les tokens | — | **-50 %** sur l'autonome | Nul (latence <1 h, invisible pour un cron quotidien) |
| **Prompt caching** | aucun | — | `cache_control` sur les system prompts. Prompts courts (~600 tokens) + appels espacés → gain marginal en solo, réel en SaaS multi-utilisateurs | — | -5 à -10 % à l'échelle | Nul |

**Bilan par prospect qualifié** : 0,045 € → **0,008-0,012 €** (÷4-6). Avec Batch API sur l'autonome : **~0,005 €**.
**Bilan mensuel actuel (330 prospects + veille)** : ~15 € → **~3 €**. Le budget de 15 €/mois qualifie alors **~1 500 prospects/mois**.

### Le principe directeur (à graver)

> **Le LLM ne doit jamais faire ce que du code sait faire, et ne doit jamais tourner avant qu'un humain (ou un score) ait décidé que ça vaut le coût.**

Concrètement : firmographie = SIRENE (gratuit) ; signaux = collecteurs (gratuit) ; score = `scoring.js` (gratuit) ; email = pattern+MX (gratuit) ; recherche LLM = seulement le haut de la file priorisée ; hooks/brouillons = seulement au moment du contact.

## 3. Pipeline de qualification — cible

### Actuel (chaîne réelle observée dans le code)

```
Import/scraping → prospect → [clic ou auto] runResearch (2 passes, par prospect)
→ fit_score LLM → NBA → [clic] generate → [clic] brief → envoi manuel
Veille : cron → analyzeAccount (par compte, redondant avec research)
Collecteurs : BOAMP/FT → company_signals → …rien (personne ne les lit)
```

### Cible : enrichissement progressif, génération différée

```
NIVEAU 0 — Gratuit, tous les prospects (millions OK)
  SIREN résolu → firmographie → business_score
  Collecteurs → company_signals → urgency_score (décroissance temporelle)
  Coordonnées → accessibility_score
  ⇒ table scores écrite, file priorisée SANS UN SEUL TOKEN

NIVEAU 1 — LLM léger, haut de file uniquement (top N/jour, Batch API)
  company_research mutualisée (Haiku + web_search, TTL 14 j, 1 fois par SIREN)
  contact_research (delta contact : prise de parole, nomination — Haiku, 1 search)
  jugement conditionnel (skip si 0 fait) → signaux typés versés dans company_signals

NIVEAU 2 — LLM riche, à la demande uniquement (action utilisateur)
  hooks + brouillons triggered (Sonnet, injecte le signal déclencheur vérifié)
  brief DISC/entourage (existant, inchangé)
```

Gains : coût ÷5, fraîcheur mécanique (les signaux gratuits arrivent tous les jours, pas tous les 14 jours), et surtout **les priorités du matin reflètent les signaux réels** au lieu d'un score LLM figé au moment de la qualif.

### Quick wins pipeline (indépendants de la refonte)

1. **Brancher `company_signals` dans `computeNba` et `computePriorities`** — aujourd'hui les signaux BOAMP/France Travail collectés chaque jour n'influencent RIEN. 1 jointure.
2. **Skip jugement si extraction vide** — 3 lignes dans `runResearch`.
3. **Écrire la table `scores`** à la fin de `runResearch` et des ingestions — le code de calcul existe déjà.
4. **Mutualiser la recherche par compte** : cache `research` par `account_id` en plus de `prospect_id`.

## 4. Optimisation des coûts (au-delà de l'IA)

- **Vercel/Supabase free tier** : OK jusqu'à ~10 utilisateurs. Le premier poste payant sera Supabase (base > 500 Mo avec les signaux). Prévoir 25 $/mois au passage SaaS — négligeable.
- **Brave 2000 req/mois** : le goulot du scraping. Mutualiser les recherches par domaine (une requête `site:linkedin.com/in "@decathlon"` sert plusieurs contacts), et ne re-scraper un compte que si `company_signals` récents (un compte sans signal ne mérite pas de scraping).
- **`checkMonthlyBudget` relit toutes les lignes `ai_runs` du mois à chaque appel LLM** — remplacer par un `select sum(cost_eur)` (RPC ou vue matérialisée). Micro-coût aujourd'hui, N+1 demain.
- **Embeddings / RAG** : PAS maintenant. Le volume (centaines de prospects) ne justifie ni pgvector ni un index sémantique. À reconsidérer uniquement pour la dédup floue à >100 k contacts (embedding des noms d'entreprise) — et même là, `pg_trgm` (déjà installé) suffit probablement.
- **JSON strict** : les sorties structurées (§2) suppriment les tokens de re-génération ET les préambules facturés.

## 6. UI — design cible

Le choix Fluent 2 est assumé et cohérent (refonte indigo+ambre). **Ne pas changer de design system** — le problème n'est pas Fluent, c'est l'exécution :

1. **Styles inline partout** (`style={{...}}` sur chaque élément, couleurs hex répétées dans chaque fichier : `#5B53E6`, `#107C10`… définis 3 fois). → Créer `lib/design-tokens.js` (couleurs sémantiques : `brand`, `success`, `danger`, `heat`) + utiliser `makeStyles` de Fluent pour les patterns répétés (chips, badges, cartes signal). Gain : dark mode réellement fiable (les hex codés en dur ne s'adaptent pas), cohérence, vélocité.
2. **Écrans cibles** :
   - **`/` Aujourd'hui** : header sobre (date, streak d'actions), pile de 5-8 cartes-action (signal + raison + 3 boutons), section "Relances en retard" en rouge, funnel réduit à une barre segmentée cliquable. Squelettes existants conservés.
   - **`/pipeline`** (nouveau) : kanban 6 colonnes, cartes compactes (nom, entreprise, score coloré, chip relance), drag & drop = PATCH statut + event. Virtualisé au-delà de 200 cartes.
   - **`/prospects/[id]`** : layout 2 colonnes — gauche fixe (identité, coordonnées actionnables, score décomposé en 4 barres avec explication, NBA) ; droite en onglets (Aperçu = synthèse + signaux datés/sourcés avec badge ✓ source vérifiée ; Messages = brouillons + historique d'envois ; Recherche = brief + faits ; Activité = timeline). Transitions `view-transition` discrètes.
   - **`/accounts/[id]`** : carte firmo SIRENE en tête (NAF, effectif, région — badge "officiel INSEE"), signaux triés par fraîcheur avec décroissance visuelle (opacité), organigramme existant, liste des prospects rattachés.
   - **`/analytics`** : inchangé sur le fond (coûts/jour, funnel) + ajouter coût par lead et taux de réponse par type de signal (les events le permettent déjà).
3. **Micro-interactions** : toasts au lieu des bandeaux d'erreur inline, optimistic updates sur les changements de statut (aujourd'hui : `load()` complet après chaque PATCH), skeletons déjà présents ✅, `prefers-reduced-motion` respecté ✅.

## 8. Prospection — le moteur du meilleur SDR

Les briques existent (NBA, signaux, heat) mais sont **débranchées les unes des autres**. Cible :

1. **Score d'urgence** ✅ (`computeUrgencyScore`) — mais alimenté par `company_signals` (collecteurs quotidiens), pas par le JSONB figé de la dernière qualif.
2. **Score de fraîcheur** : `exp(-age/H)` existe — l'exposer en UI (opacité/badge "il y a 3 j").
3. **Score d'intention** = somme pondérée des signaux `rfp_it`/`recrutement` récents — c'est `urgency` restreint aux types transactionnels. 10 lignes dans scoring.js.
4. **Détection de comptes chauds** : vue SQL `hot_accounts` = comptes avec signal < 14 j sans prospect contacté < 30 j. **C'est LA requête qui génère des RDV** — elle est enfin possible car `company_signals` est relationnel.
5. **Suggestions quotidiennes** : la section Priorités devient la page d'accueil entière (§5), avec raison sourcée par template déterministe (`"RFP {detail} publié le {date} (BOAMP)"`) — jamais par LLM (zéro hallucination sur le "pourquoi").
6. **Priorisation automatique** : trier la file de qualification autonome par `business_score × signaux` au lieu de FIFO (`auto-qualif.js` prend aujourd'hui les 500 premiers `researched_at IS NULL` sans tri).

## 9. Scraping

Le pivot Brave-snippets (ne pas fetch LinkedIn, ne pas scraper DDG) est la bonne architecture — les leçons du README sont justes. Améliorations :

1. **Prioriser la file de scraping par valeur** : scraper d'abord les comptes avec signaux récents (un compte chaud sans contact vaut plus qu'un compte froid). Aujourd'hui : tous les comptes `auto_watch` à la même fréquence (30 j).
2. **Mutualiser les requêtes Brave** : une recherche par (entreprise × rôle-type) plutôt que par contact espéré ; parser tous les profils du snippet set.
3. **Cache des SERP** : stocker les réponses Brave brutes (JSON) 30 j — un re-scan ne re-consomme pas le quota si la SERP est fraîche.
4. **Qualité poste** : le poste "best-effort" des snippets devrait être marqué `role_confidence: incertain` systématiquement, et corrigé par la qualif 2 passes (déjà le cas implicitement — le rendre explicite en base).
5. **Nouvelles sources gratuites** : INPI/RNE (dirigeants officiels, open data) pour les DG/DAF — complète LinkedIn pour les ETI discrètes ; annuaires de conférences IT (les intervenants DSI/RSSI sont publics et datés).

## 10. Prompt engineering

Hygiène générale bonne (anti-fabrication martelée, JSON exigé, datation/sourçage systématiques). Faiblesses et réécritures :

### 10.1 Faiblesses transverses

1. **Le schéma JSON est décrit en prose dans le system prompt** (~40 % des tokens de chaque prompt) puis re-parsé au slice d'accolades. → **Sorties structurées** : déclarer un tool avec `input_schema` JSON Schema et forcer `tool_choice`. Supprime : la description du format dans le prompt (-300 à -500 tokens/appel), `extractJson`, la passe de réparation, et les enums invalides (le schéma contraint).
2. **Fenêtre 12-18 mois trop large** dans extraction/brief : un signal de 14 mois a une fraîcheur ~0,1 dans le scoring — il ne sert à rien mais coûte des tokens de sortie. → "9 derniers mois, sauf réglementaire".
3. **Le jugement re-copie les faits en signaux** : la transformation fact→signal est quasi mécanique (type, detail, date, source sont déjà dans le fait). → Le mapping devient du code ; le LLM ne produit plus que `summary`, `fit_reason` et le tri par pertinence. Sortie divisée par 3.
4. **Hooks dans le jugement** (cf. §2) → déplacés dans generate, avec le signal déclencheur.

### 10.2 Extraction réécrite (Haiku, sorties structurées)

```
Tu es un extracteur de faits pour la prospection B2B IT France.
Recherche sur le web l'actualité des 9 derniers mois (18 mois pour le
réglementaire) de l'entreprise {company} et du contact {name} ({role}).

Cherche dans cet ordre : offres d'emploi IT/cyber/cloud ouvertes ;
projets SI annoncés ; nomination DSI/RSSI/CTO ; levée/croissance ;
incident cyber ; obligation NIS2/DORA/HDS du secteur ; prise de parole
du contact.

Règles : uniquement des faits publics, datés, avec l'URL exacte de la
source. Aucune déduction. Si rien de solide : facts=[] et dis ce que tu
as cherché dans search_notes.
```
(Le format de sortie vit dans le JSON Schema du tool, plus dans le prompt.)

### 10.3 Point de vigilance : le profil DISC (brief P4)

Établir un **profil psychologique** d'une personne à partir de ses traces publiques est du profilage au sens RGPD — base légale fragile en intérêt légitime, et risque d'image sérieux si un prospect l'apprend. Recommandation produit : reformuler en **"style de communication observé"** (factuel : "communique en données chiffrées dans ses interviews") sans taxonomie DISC ni inférence de personnalité, et documenter ce traitement dans la LIA. Même valeur commerciale, risque divisé.

## 11. Base de données

### Problèmes par gravité

1. **`events` défini deux fois** (v1 : partitionné `(id, occurred_at)` ; v3 : non partitionné) — les deux `if not exists` → le schéma dépend de l'historique d'exécution. **Geler le vrai schéma** (`supabase db dump`) et repartir en migrations CLI versionnées (`supabase/migrations/` + CI). C'est le prérequis de tout le reste.
2. **`accounts` + `companies`** : fusionner (§1.2). Plan : ajouter `accounts.company_id` (fait ✅) → backfill par résolution SIREN → basculer les FK (`prospects.account_id` → `company_id`) → vue `accounts` de compat → drop.
3. **Table `scores` morte** : soit on l'écrit (recommandé), soit on la supprime — un schéma qui ment est pire qu'un schéma incomplet.
4. **Dédoublonnage en RAM** (`POST /api/prospects` charge toute la table) : contraintes `unique` partielles sur `lower(email)` et `linkedin_url` + `insert ... on conflict do nothing` → O(1) et fiable sous concurrence.
5. **Dates en texte** : `account_contacts.data_date` (TEXT "YYYY-MM"), dates de signaux JSONB parsées par regex FR dans `scoring.js` (`parseSignalDate` gère "mars 2024" !). `company_signals.observed_at` est un vrai `date` ✅ — la migration des signaux (§3) résout le problème à la racine.
6. **Index manquants** pour les tris réels : `prospects (fit_score desc)` (tri priorités), `prospects (status, created_at desc)` (liste filtrée), `ai_runs (created_at)` couvre le budget ✅.
7. **Multi-tenant** : `org_id uuid not null` sur toutes les tables métier + policies RLS `org_id = auth.jwt() ->> 'org_id'` — à poser AVANT que le volume rende le backfill pénible.

## Annexe — ce qu'il ne faut PAS faire

- **Ne pas réécrire la stack** (Remix, tRPC, monorepo…) : Next+Supabase+Vercel est adapté ; le problème est dans le modèle de données et le câblage, pas le framework.
- **Pas d'embeddings/RAG maintenant** : volume insuffisant, `pg_trgm` couvre la dédup.
- **Pas de multi-agents orchestrés** : le pipeline cible est une file + du code déterministe + 2 appels LLM ciblés. La complexité agentique n'apporte rien ici.
- **Ne pas automatiser l'envoi** : "l'envoi reste manuel" est un choix de conformité ET de délivrabilité qui protège le produit — le garder comme argument commercial.
- **Ne pas supprimer le harnais d'eval** : c'est lui qui rend les bascules de modèle (Sonnet→Haiku) sûres. Chaque changement de prompt/modèle passe par `npm run eval` avant merge.
